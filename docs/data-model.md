# Data Model

## Overview

Each microservice owns its own MongoDB database and defines its own Mongoose schemas. The data model is intentionally domain-based and simple.

## Catalog Service

### Cake model

File: catalog-service/src/models/cake.model.js

Fields:

- name: String, required, trimmed, length 2-100
- description: String, required, trimmed, max 500 characters
- category: String, required
- price: Number, required, minimum 0
- availability: Boolean, default true
- imageReference: String, optional
- timestamps: true

This is the main product catalog model used by the storefront.

## Order Service

### BasketItem schema

Embedded within basket items.

Fields:

- cakeId: String, required
- name: String, required
- price: Number, required, minimum 0
- quantity: Number, required, minimum 1
- _id disabled for embedded items

### Basket model

File: order-service/src/models/basket.model.js

Fields:

- userId: String, required, unique
- items: array of basket items, default []
- total: Number, default 0
- timestamps: true

This model stores the user’s current basket state.

### Order model

File: order-service/src/models/order.model.js

Fields:

- userId: String, required
- items: array of order items
- total: Number
- status: String, enum ["PENDING", "COMPLETED", "CANCELLED"]
- timestamps: true

The order created during checkout copies the basket items and price totals into a new order record.

## Rating Service

### Rating model

File: rating-service/src/models/rating.model.js

Fields:

- cakeId: String, required
- userId: String, required
- rating: Number, required, min 1, max 5
- review: String, optional
- timestamps: true

This model stores a review and rating for a cake. There is no direct relational join with the catalog data.

## Notification Service

### Notification model

File: notification-service/src/models/notification.model.js

Fields:

- userId: String, required
- orderId: String, required
- message: String, required
- status: String, enum ["PENDING", "SENT"], default "SENT"
- timestamps: true

This model captures order completion notifications generated by the event-driven workflow.

## Databases Used

| Service | Database |
| --- | --- |
| Catalog | cake_catalog_db |
| Order | cake_delight_orders |
| Rating | cake_rating_db |
| Notification | cake_delight_notifications |

## Data Ownership

Each service is authoritative for its own data:

- Catalog owns the cake catalog
- Order owns basket and orders
- Rating owns rating records
- Notification owns notification records

This separation is a core microservice design pattern and keeps the application modular, even though the frontend presents it as one experience.
